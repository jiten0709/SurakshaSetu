# OmniRoute hardening (TDD §1.6)

SurakshaSetu's model gateway is its own OmniRoute container. It is service `omniroute` in `infra/compose.yaml`, under profile `gateway`, on `127.0.0.1:20130`. It fronts the chat routes only; embed and rerank go straight to TEI (TDD §1.5, decided in Step 8).

**Pinned release:** `diegosouzapw/omniroute:3.8.50@sha256:085c57ad…`, an OCI index for arm64 and amd64. Every statement below was checked against that release's source.

**Where the settings live:**

- **Container environment:** `infra/compose.yaml`. OmniRoute reads these variables at start-up.
- **Everything else:** the gateway's SQLite database, which is set through its admin API. Git holds the values in `seed.json`.
  - `make gateway-up` starts the container and runs `orchestrator/scripts/omniroute_seed.py apply`. That imports the connection, combos and app key, sets each settings section and the key's policy, then reads everything back. With `--live` (the live instance only) it also sets the overlay's payload rules (see "Live instance").
  - `make gateway-verify` does only the read-back. It exits 1 on any drift, because OmniRoute answers 200 to keys it drops.
- **Tests:**
  - `orchestrator/tests/unit/test_omniroute_hardening.py`: checks the Git side, with no network.
  - `orchestrator/tests/stack/test_omniroute_stack.py` and `test_gateway_stack.py`: check the running gateway.
  - A unit test fails if a test named below doesn't exist.

## Guardrails: why `warn`, and why PII masking is on everywhere

OmniRoute's built-in guardrails are thin: English regular expressions for injection, and PII patterns for email, card numbers, Brazilian CPF/CNPJ/phone and US SSN (no Aadhaar or PAN). The primary rails are the orchestrator's (TDD §4.2, Step 10).

- **Injection guard in `warn` mode** detects and logs but does not block. In 3.8.50, `block` applies to every route and ignores per-request opt-outs. That would stop `guard-input` from ever seeing the attacks it exists to classify, and a system prompt that says "never reveal your system prompt" would be blocked on every call.
- **PII masking is on for every route.** On the redacted routes it is a second pass after Presidio. On the self-hosted routes it masks emails and card- or phone-shaped numbers before the model; no S0–S3 slot needs them.
  - If the masker ever changes a gen-route envelope, the model saw less than the audit log recorded, and only where the first line missed something.

## How OmniRoute 3.8.50 behaves (read in its source, confirmed by the stack tests)

- **`x-omniroute-compression`** is on every chat response: `off; source=off` when compression is disabled. When compression runs, the value is `<mode>; source=<source>`, and rewrite rules append `; tokens=a->b; rules: …`.
  - Upstream `x-omniroute-*` headers never reach the client, so a stub-injected header cannot prove the adapter's rejection end to end.
  - The unit tests prove it with the real formats, and a stack test shows a client can't switch compression on.
- **The response `model`** is the combo target's model id (`stub-guard`), not what the upstream answered and not the combo name. So each combo targets its own stub id, and the stub maps it back to the route.
- **`user` is forwarded unchanged**, so no session marker is needed. The `X-SS-*` headers are not forwarded, and nothing downstream needs them.
- **No fallback count is reported on chat** (`X-OmniRoute-Fallback-Attempts` is set only for image, speech and video), so `GatewayResult.fallback_hops` stays 0.
- **A single-target combo retries once after 2 s by default**, and a failure may cool the connection down for about 3 s.
- **Keys can be imported with a chosen value.** That is how the app key equals `SS_GATEWAY_API_KEY` and never appears in Git. The import resets the key's restrictions, so the seed always re-applies the policy afterwards.

## Not carried by the gateway

`embed` and `rerank` are not combos. OmniRoute hosts no embedding or rerank models, and its `/v1/rerank` speaks the Cohere/Voyage shape. The adapter calls `tei-embed` and `tei-rerank` directly on the self-hosted network (`SS_TEI_EMBED_URL`, `SS_TEI_RERANK_URL`).

## Live instance (`omniroute-live`)

The self-hosted routes' live configuration (Step 1.5b, design E, D-1) runs on a second, ephemeral OmniRoute: service `omniroute-live`, profile `gateway-live`, `127.0.0.1:20131`.

- `make gateway-live-up` creates it empty and seeds it with `seed.json` + `seed.live.json`, merged in memory.
- `make gateway-live-down` saves its log to `orchestrator/.cache/live-gateway-<ts>.log` and removes it.
  With `LIVE_LOG` set it saves there instead: `make eval-live-self-hosted` sets it to its run's exact path, named by its report's stamp.
- `make check-gateway-live` does both around `tests/stack/test_gateway_live_stack.py`.
- It starts with `--no-deps` and never starts the `stubs` service. They must already be running: the stack test fails at setup with a message when they are down, and without them the gateway log shows `ENOTFOUND stubs`.

What holds:

- **Isolation.** A separate container with its own database. `omniroute`, its volume `omniroute-data` and `seed.json` are never started, stopped, recreated, mounted or written by a live target. Every Docker call is `docker compose --profile gateway-live <command> omniroute-live`. No recipe passes `-v` or names a volume. The seed script writes to :20131 only with `--live`, and refuses :20130 with it. `omniroute`'s compose definition is frozen in a test, because any change to it recreates the stub container.
  Tests: `test_omniroute_hardening.py::test_the_stub_instance_is_unchanged`, `test_omniroute_hardening.py::test_the_live_targets_touch_only_the_live_instance`, `test_gateway_live_stack.py::test_the_protected_infrastructure_is_unchanged`.
- **No volume.** Its SQLite database and the `server.env` OmniRoute writes at boot live in the container layer and die with it. Every run starts from the seed alone, and nothing is kept at rest.
  Test: `test_omniroute_hardening.py::test_the_live_instance_is_the_same_gateway_with_no_state_of_its_own`.
- **Same gateway.** The same digest, healthcheck and hardening env as `omniroute` (a duplicated block, not a shared anchor), plus `OMNIROUTE_DIRECT_HEADERS_TIMEOUT_MS=105000`.
- **Two connections, one target per combo, no fallback.** `vllm` → the stubs (`gen-converse`, `gen-recommend`; they stay on the stubs, O4). `ollama-local` → the host's Ollama at `host.docker.internal:11434` (`guard-input`, `nlu-extract`, `summarise` as `ollama/<model>`; `verify-claims` as `ollama-local/<model>`, the two target forms U7 tested). Each combo has exactly one target and no `globalFallbackModel` exists, so a failed self-hosted route fails closed and does not fall over to the stubs.
  Tests: `test_omniroute_hardening.py::test_the_live_overlay_adds_one_connection_and_moves_only_the_self_hosted_routes`, `test_gateway_live_stack.py::test_a_self_hosted_route_fails_closed_without_fallback`. The stack test ran on 2026-11-15 with no Ollama on the host: `guard-input` returned 502 and nothing reached the stubs. It has not run against a running Ollama.
- **The 105 s response-start bound (O2, D-2).** Without it the fetch layer waits 30 s and re-sends once (row 15). 105 s is above 15× the largest chat budget (gen-recommend 6 s → 90 s; 15× is the cap of `SS_GATEWAY_TIMEOUT_SCALE`) and below OmniRoute's 120 s combo timeout, so the adapter gives up first. An upstream slower than 105 s is still sent twice and fails at 120 s (U7, 2026-11-13). Only the live instance has the bound.
  Test: `test_omniroute_hardening.py::test_the_bound_sits_between_the_scaled_budgets_and_the_combo_timeout`.
- **The model and thinking off (C5b, 2026-11-19).**
  - **The model:** Ollama's `qwen3.5:4b-q4_K_M`, manifest `sha256:d8b0f5e9760cd1682034f292d7ef72ec46f432149be0df7574bf2d6e92e38c04`, on Ollama 0.40.16. It serves all four self-hosted routes. `apply --live` still refuses a model left as `__UNSET__`.
  - **Thinking off:** `seed.live.json`'s `payloadRules` adds `reasoning_effort: "none"` (decision 7) and `temperature: 0` (decision 4) for that **bare** model name. A prefixed name (`ollama/…`) doesn't match, and nothing reports that it didn't (payload-rules probe, 2026-11-17).
  - **Storage:** rules persist only through `PUT /api/settings/payload-rules`. `PATCH /api/settings` drops them with a 200.
  - **Read-back:** `verify --live` reads them back. Every non-empty section must equal the seed's exactly, so a dropped rule is drift. The stub seed has no rule, so `gateway-up` and `gateway-verify` never send that request.
  - **The stack test** swaps the model's name for a never-pulled placeholder, so the rule names the placeholder and its read-back runs against 3.8.50.

    - that a name containing `.` and `:` matches (the probe used names like `ss-probe-a`; S0 Part 2's captured request settles it);

  Tests: `test_omniroute_hardening.py::test_the_live_payload_rule_adds_only_thinking_off_for_the_one_self_hosted_model`, `test_omniroute_seed.py::test_the_live_apply_puts_the_payload_rules_and_the_stub_apply_never_does`, `test_omniroute_seed.py::test_payload_rules_are_read_back_exactly`.
- **Ollama's context (D-6, revised 2026-11-20 for bug #44).** Ollama's default context is 4,096 tokens and it truncates silently with HTTP 200 (U4). The host must run it with `OLLAMA_CONTEXT_LENGTH=8192`. Nothing in the gateway sets or checks that. The adapter does, when `SS_GATEWAY_CONTEXT_TOKENS` = N is set (dev/test only; pilot and prod refuse it):
  - **On the four self-hosted chat routes** (`CONTEXT_FLOOR_ROUTES`: guard-input, nlu-extract, verify-claims, summarise), a reply whose `usage.prompt_tokens` reaches **N // 2** (4,096 at 8,192) fails closed with `CONTEXT_TRUNCATED`. Ollama 0.40.16 cuts a prompt longer than N − 1 tokens to N − max((N − keep) // 2, 1) and reports that count (`llm/llama_server.go:320–357`; S0 Part 2 run 2: 18,727 → 4,098), which is never below N // 2 for any keep; 0.20.2 reported N itself (U4). Genuine prompts of N // 2 to N − 1 tokens are refused too (the owner's safety-over-capacity decision).
  - **Every other chat route** keeps the whole-context check (`prompt_tokens` ≥ N), so gen-converse and gen-recommend (the stubs' word count) behave as before.
  - No `prompt_tokens` fails closed with `MALFORMED_RESPONSE` on any route; unset, nothing is checked.
  - **Ollama's message dropping, on guard-input's output mode (approved 2026-11-20, bug #44).** When a whole conversation exceeds N, Ollama drops its oldest non-system messages (`server/prompt.go:21–86`; logged at DEBUG only) and reports what remains, which can be anything up to N. Only guard-input's output mode (`[system, customer turn, assistant reply]`) has such a message. With D-6 set, a turn is **over the output-guard size limit** when **M(c) > N // 2 − 64** (4,032 at 8,192; equal passes), where `c` is the exact `stored_raw` that `call_guard` sends (after the orchestrator's NFKC normalisation and redaction) and **M(c) = UTF-8 bytes + 10 × count('@') + ⌊3 × ASCII digits / 5⌋** (`gateway.adapter.masked_size`). **Only that call is affected (route-specific, corrected 2026-11-20):** the input rails, slot taking and every other route are unchanged. `rails.output.release`, the only caller of the output-mode guard, drops an over-limit turn's draft before any rail, so nothing is verified, regenerated or guarded and the existing fallback renders (S1/S2: the question alone; S3: the deterministic card; a side query: the abstain line) — audited `RC-GUARD-SIZE` `fallback`. Compose withholds the gen-converse lead sentence for such a turn (an enter hook, a resume or G1–G3 included), so no such draft is made — `RC-GUARD-SIZE` `skipped`. The customer is not asked to shorten (the turn's slots are already taken). Unset, nothing changes; no route's request and no gateway check changes.
    - **Why it holds, for Qwen3.5 4B (`qwen3.5:4b-q4_K_M`) on Ollama 0.40.16 (llama.cpp `6c01da627`) behind OmniRoute 3.8.50 only** (decision log, bug #44):
      1. The `qwen3.5` renderer with thinking off writes `[S, U, A]` as S's block, then `<|im_start|>user\n` u `<|im_end|>\n`, then `<|im_start|>assistant\n` a; without U, the same minus U's block (`qwen35.go:226–310`).
      2. Both of Ollama's counts tokenize that string with `parse_special` on: `/tokenize` for the dropping decision, `/completion` for the reported count (`server-context.cpp:6400–6401`, `server-common.cpp:1109–1112`). The model adds no BOS.
      3. llama.cpp splits the text at every control token and tokenizes each piece alone (`llama-vocab.cpp:3645–3720, 3896–3915`). `<|im_start|>` and `<|im_end|>` are control tokens; every special token's text has `<` only at position 0, so no match crosses a role marker; no strip attribute applies (`general.name` is `Source`). So adding U adds exactly `<|im_start|>`, `"user\n" + u`, `<|im_end|>` and `"\n"`: Δ = 2 + τ("user\n" + u) + τ("\n"). **The boundary effect is 0.**
      4. Every token covers at least one byte (byte-level BPE: no empty token, all 256 byte symbols present, unknown symbols fall back to ≤ 1 token per byte), so **Δ ≤ bytes(u) + 8**.
      5. A drop happens only when the whole prompt is over N tokens and leaves `[S, A]`: what remains is ≥ N + 1 − Δ (or, over N − 1, the runner cut, which the floor catches). So whenever **Δ ≤ ⌈N/2⌉ + 1**, the reported count is ≥ N // 2 and the floor fails the call closed.
      6. OmniRoute 3.8.50's PII masking rewrites `c` before Ollama (`inputSanitizer.ts:76–105, 225–240`): an email (one '@', ≥ 6 bytes) becomes 16 bytes, a phone number (≥ 10 ASCII digits) 16, an SSN (9 digits) 14; card, CPF and CNPJ replacements are no longer than their match; replacements create no match and a second pass changes nothing. So **bytes(u) ≤ M(c)** (Ollama's trimming only shortens). With M(c) ≤ N // 2 − 64: Δ ≤ 4,040 against the 4,097 allowed at 8,192, 57 tokens spare.
    - **Limits, stated plainly:**
      - The proof covers Qwen3.5 4B only. **It is not evidence for any other model**: each candidate must re-establish the protocol's S0 (b) checklist (`docs/drafts/self-hosted-model-protocol.md`) before this protection is relied on for it.
      - It also covers only Ollama 0.40.16 with llama.cpp `6c01da627`, and only OmniRoute 3.8.50's six patterns. The masking constants are tied to `VERIFIED_IMAGE` (`OUTPUT_GUARD_MASKING_IMAGE`): an image change fails the tripwire test and bug #43's gate, until the patterns are read again.
      - D-6 is dev/test only. Pilot and prod refuse the setting, and with it the limit, so this says nothing about a production guard.
      - M(c) is an upper bound, not the exact masked length: a turn near the limit may lose its generated text although its real masked text would fit (fail closed).

## Deployment gates (not provable on a laptop)

- **Egress:** enforce the provider allowlist at the network layer; don't rely on gateway configuration alone (TDD §1.6).
- **Admin access:** SSO (OIDC) in front of the admin UI and API, reachable from the ops network only.
- **HA:** 3.8.50 is one Node process writing one SQLite file, so there are no replicas or rolling restarts. Confirm the HA model before production.
- **Supply chain:** build the image internally from the pinned release and scan its SBOM.
- **Real secrets:** replace the compose dummies (`OMNIROUTE_*`) and `SS_GATEWAY_API_KEY`.
- **Production routes:** the model pools and providers in `routes.prod.example` (D2). Each is a combo target that passes the evaluation gate end to end through the gateway.

## Upgrading the image

When bumping the pinned release, re-check each of these in the new source, and rerun `make gateway-up`, `make gateway-verify`, `make check-gateway-live` and the stack tests:

- the keyless provider list (`src/shared/constants/providers/noauth.ts`) against `settings.blockedProviders`;
- the compression header format;
- the response `model` rewrite;
- the flat `semanticCacheEnabled` key;
- whether `vllm` still passes `json_schema` through;
- `resolveDirectHeadersTimeoutMs`: that `OMNIROUTE_DIRECT_HEADERS_TIMEOUT_MS` still sets the response-start wait, and that the single re-send is unchanged (U7);
- the `ollama-local` passthrough: that a connection with `authType: apikey` still imports and reads back with 0 drift, and that both target forms (`ollama/…`, `ollama-local/…`) still resolve to it;
- payload rules: that `PUT` and `GET /api/settings/payload-rules` still store and list them, that `PATCH /api/settings` still drops them, and that a bare rule name still matches both target forms.
